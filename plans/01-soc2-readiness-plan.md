# SOC 2 readiness analysis and resolution plan

Assessment date: 2026-09-04. Status: proposed controls and remediation; no attestation opinion. Proposed accountable sponsor: organization leadership. Control owners below are roles to assign, not assertions about existing staff.

## Conclusion and engagement boundary

OpenGlasses has useful application safeguards, including device Keychain storage, protected conversation files, authenticated encryption, tool confirmation, remote-command rate limits, and structured logging. The reviewed source also contains material transport, outbound-fetch, MCP authorization, and audit-evidence gaps. These prevent this review from supporting a readiness conclusion for a system that includes the affected features. Organization-wide operating effectiveness remains unassessed: repository contents cannot establish whether personnel, cloud, supplier, incident, or governance controls operate.

SOC 2 is an attestation examination of a defined service organization's system. An iOS application, an open-source repository, or a privacy setting does not by itself receive a SOC 2 certification. Management must identify the legal entity, service commitments, users, system boundary, and responsible operators before commissioning the examination. [AICPA SOC 2 overview](https://www.aicpa-cima.com/topic/audit-assurance/audit-and-assurance-greater-than-soc-2/).

Use the **2017 Trust Services Criteria with revised points of focus—2022** and the **2018 Description Criteria with revised implementation guidance—2022** as the engagement baseline, subject to the service auditor's confirmation. Official public resource pages were checked; their account-gated downloads were not retrieved. The mapping below is an analyst's project-specific working crosswalk, not reproduced normative criteria or a substitute for the authoritative documents. [AICPA Trust Services Criteria](https://www.aicpa-cima.com/resources/download/2017-trust-services-criteria-with-revised-points-of-focus-2022), [AICPA Description Criteria](https://www.aicpa-cima.com/resources/download/get-description-criteria-for-your-organizations-soc-2-r-report).

Proposed scope: **Security, Confidentiality, and Privacy**, because the product handles conversations, camera/audio content, stored personal information, and disclosures to configurable services. Management and the auditor must decide whether **Availability** and **Processing Integrity** are included from actual customer commitments and processing responsibilities; they cannot be dismissed simply because the client runs on a phone. These categories are especially relevant if the organization operates gateways, relays, hosted services, scheduled tasks, or processing workflows for customers.

Define each boundary explicitly:

| Component | Proposed treatment and decision required |
| --- | --- |
| iOS app, watch/share/widget extensions, local stores | Include development, release, privacy and security behavior. Identify supported deployment modes and what local data the operator can access. |
| GitHub, build services, Apple distribution, signing keys | Include organization-controlled access and release operations; document supplier dependencies and inherited controls. |
| Organization-operated gateway, model endpoint, relay, hosting, licence portal | Include if used to deliver the scoped service. Obtain actual inventories and deployment configurations; presence of source does not prove an environment exists. |
| User-operated OpenClaw/Hermes/MCP/model endpoints | Describe the customer-managed boundary, installation requirements, data flows, and customer responsibilities. Do not imply these endpoints inherit the operator's assurance. |
| Cloud model, speech, telemetry, storage, and other suppliers | Decide whether each is a subservice organization or another external party, define the treatment, inspect agreements and assurance, and identify downstream recipients. |
| Glasses, companion app, iOS security, customer device administration | Record reliance and complementary user responsibilities, including supported firmware, passcode/device-lock requirements, permissions and network conditions. |
| Internal personnel and support | Include access to production, signing material, customer diagnostics, exports, and support systems where applicable. |

The system description should inventory software, infrastructure, people, procedures and data; explain material flows, operating locations, service commitments, boundaries, relevant incidents/changes, exclusions and dependencies; and identify applicable complementary user and subservice-organization controls. Complete a separate DC-200 checklist against the authoritative description criteria before auditor review. An architecture README alone is insufficient evidence of the final description.

## Evidence method

- **I — Implementation observed:** source implements an identifiable safeguard. This is design evidence, not proof that a release or production deployment uses it correctly.
- **G — Gap observed:** source directly shows a missing safeguard or behavior inconsistent with the proposed control objective.
- **U — Unverified:** no sufficient operating evidence was examined. This does not mean the organization lacks the control.
- **D — Scope decision:** management and the auditor must establish applicability before evaluating sufficiency.

This review read source, configuration, selected tests, workflows and existing plans. It did **not** execute application tests, run the app, capture network traffic, assess live infrastructure, inspect secret contents, interview personnel, examine customer contracts or review a reporting-period sample. Test filenames below indicate available test assets, not passing results. Findings describe observed paths and prerequisites, not a claim that exploitation occurred.

## Type 1 and Type 2 readiness gates

The engagement must distinguish an assessment of design at a specified date from an examination that also evaluates operation over a specified period. Management and the independent CPA service auditor must agree the engagement, reporting period, sampling and evidence requirements. There is no guaranteed universal 30/90-day path or fixed evidence period supplied by this plan. The [AICPA SOC 2 reporting guide](https://www.aicpa-cima.com/cpe-learning/publication/soc-2-reporting-on-an-examination-of-controls-at-a-service-organization-relevant-to-security-availability-processing-integrity-confidentiality-or-privacy-OPL) is the authoritative engagement guidance to use with the criteria.

**Before a proposed Type 1 examination date:**

1. Approve the scoped service, commitments, criteria/categories, system description, risk treatment and owners.
2. Address material design gaps in every in-scope route, including P0 exposure. A feature may be explicitly excluded/disabled only when the service boundary and released behavior support that decision.
3. Verify installed controls in the actual scoped release and environments, including policy enforcement, access configuration, secrets, vendors, data flows and logging.
4. Complete readiness walkthroughs and independent technical review; record remaining exceptions with owners and their effect on commitments. Management acceptance does not determine the auditor's opinion.
5. Prepare management's assertion and obtain the auditor's assessment of whether sufficient appropriate evidence exists for the proposed date.

**Before and during a proposed Type 2 period:**

1. Establish control operations and complete evidence populations before starting the agreed observation period.
2. Retain evidence throughout that period, including changes, failures, exceptions, nonoccurrence and compensating action. Do not backdate records or relabel plan approval as historic operation.
3. Exercise controls whose ordinary events are rare and identify those as exercises; the auditor determines what this evidence establishes.
4. Track significant system/control changes and whether populations or periods require separate treatment; resolve missing evidence and sample exceptions transparently.
5. Reconcile the final system description, management assertion, control matrix and service auditor's testing. A passing code test or completed plan does not establish operating effectiveness for untested organizational controls.

This document is complete as a readiness plan when owners accept it, its evidence references are reconciled to the release baseline, and W01–W08 turn the proposed actions into tracked work. SOC 2 readiness itself remains conditional on implementation, operating evidence and the independent examination.
