## P1 — Marking cores and export writers (headless)

1. **`AIProvenance` standard metadata.** Extend `pdfDocumentInfo` with `kCGPDFContextTitle` (the document's own title, passed in), `kCGPDFContextKeywords` containing `AI-generated`, and add `xmpPacket(title:) -> Data`: a minimal XMP with `xmp:CreatorTool`, `dc:description` (the footer line), `xmp:CreateDate`, and `Iptc4xmpExt:DigitalSourceType` = `http://cv.iptc.org/newscodes/digitalsourcetype/trainedAlgorithmicMedia` (the IPTC value the provenance ecosystem reads as "generated by a trained model"); for documents that mix human speech-to-text with model text use `.../compositeWithTrainedAlgorithmicMedia`. One shared helper, `PDFProvenanceStamp.apply(to context: CGContext, provenance:, title:, composite:)`, calls `CGPDFContextAddDocumentMetadata` inside the renderer block; the four existing renderers call it. Tests: the XMP parses, carries the digest and the IPTC URI, contains no instruction text (reuse the canary pattern in `AIProvenanceTests`), and the PDF's Info dictionary read back through PDFKit shows title, creator, subject and keywords.
2. **Medical export provenance.** Add `enum MedicalExportOrigin { case automaticTranscription, modelAuthored(AIProvenance) }` and thread it from the tool: the `transcript` argument → `.modelAuthored(AIProvenance.forActiveModel(...))`, the recorder path → `.automaticTranscription`. Each format states it: PDF (document info plus XMP via item 1, `composite` for STT, trained-algorithmic for model text, and a printed line above the transcript), FHIR (`meta.tag` with a system/code pair for the origin and the model identifier, and the same sentence appended to `description`; applied to the POST too), HL7 (an `NTE` segment after `TXA`), plain text (a first line). "Automatic transcription" is not an AI-generated-content claim: Art. 50(2) exempts text that does not substantially alter the input, and the line says what it is. Tests through the existing medical export tests with both origins across all four formats, including that the FHIR POST body carries the tag.
3. **Recording metadata and the audio gate.** `CaptureAudioRouter` latches `assistantVoiceMayBeIncluded` (true once the gate passes a buffer while TTS speaks on the phone speaker, or simply when `captureIncludesAssistantVoice` is on at start, whichever is implementable before `startWriting`). `VideoRecordingService` and `AudioRecordingService` set `writer.metadata` before `startWriting` with `commonIdentifierDescription` = "May contain synthetic speech from Avenkin AI." and `quickTimeMetadataSoftware`/the iTunes equivalent = app identity, only when the flag is on; a recording without the assistant's voice gets no claim. Route `AudioRecordingService` through `AssistantAudioGate` the way `CaptureAudioRouter` does, so the "Include Assistant Voice" setting is true for audio-only recordings too. The recorded-job `BundleManifest` gains `assistant_voice_included: Bool` derived from the timeline. Tests: gate decision for the audio-only path, metadata present/absent by flag (read back with `AVURLAsset.load(.metadata)` on a tiny written file), manifest flag.
4. **Model text that is saved or shared.** `SavedNote` gains `origin` (`"assistant"`) and `NotesTool` sets it; the Notes list shows a small "AI" tag from it. `notes_vault` entries get a trailing marker line `_Written by Avenkin AI from your dictation._` under the existing `## <iso>` heading. The chat transcript share gains a header line after the date: `Assistant turns are AI-generated by <model>` (model from the thread's recorded identifier where present, else "Avenkin AI"). The agent archive writes an HTML-comment header into `soul.md`, `skills.md` and `memory.md` naming the archive's provenance (`<!-- ai-generated: see provenance.json -->`). Tests for each.
5. **Feasibility record.** A short section in this plan (below, "Marking decisions") recording why there is no audio watermark on live TTS, no marking of AI-drafted SMS/WhatsApp/email bodies, and why RTMP has no file to mark. Dated, so it can be shown.

## Marking decisions (feasibility record, 2026-10-07)

- **Live TTS through the glasses or phone speaker** is played from memory and never written by the app. There is no file to mark, and an audible watermark on every spoken answer would degrade the one accessibility channel the Accessibility tier depends on. Art. 50(2) applies "to the extent technically feasible" with proportionality for SMEs; the marker is applied at the point where the voice becomes a file (item 3).
- **AI-drafted SMS, WhatsApp, Telegram and email bodies** are reviewed, edited and sent by the wearer, are typically under the length the Guidelines treat as metadata-only, and travel on channels that carry no metadata. Not marked; the recipient receives a human-sent message.
- **RTMP broadcast** is a live stream with no file; the platform's title field is the deployer's to set. Not marked by the app.
- **Camera stills** carry no model content and are not synthetic. Not marked.
