# OpenGlasses Feature Plans

This is the canonical home for all OpenGlasses feature plans. Plans are lettered in creation order:
**A–Z**, then **AA, AB, AC…** as the alphabet runs out. Each row links to the full plan doc; the
detailed status, scope, and open questions live there. House style: a deterministic, headless-testable
core first, with the live/device/backend edge deferred; one PR per plan.

**Legend:** ✅ Shipped · 🚧 Core shipped / partial (live or follow-up edge deferred) · 📋 Planned · 📝 Drafted (not scheduled)

| [CW](CW-realtime-audio-rig-recovery.md) | Realtime Audio Rig Recovery | 🚧 Core shipped — **a realtime reply queued when the audio route settles is no longer discarded silently.** A glasses HFP mic arriving at session start reads as `.newDeviceAvailable`, which forced a full graph rebuild and destroyed the already-scheduled first reply — the symptom being *"it didn't speak the first time, then it worked every time after"*, which reads as a flaky backend rather than an audio-rig bug. **P1** pure `AudioGraphRecovery` (four rules over an observed graph state → `.none`/`.restart`/`.rebuild(carryPlayback:)`), so a stopped engine is no longer confused with a broken graph and the scheduling and recovery paths can no longer disagree about what a dead engine means; **P2** `PendingPlaybackMirror` — a bounded, pure mirror of what the player node still owes, re-scheduled onto the new graph **under the original generation** so played-accounting stays continuous, and when carry-over is impossible the lost milliseconds are **reported** into the same truncate-on-loss path barge-in uses rather than swallowed (a reply the wearer never heard must not sit in the model's context as though they had); **P3** voice processing disabled before an engine is dropped, and a restart that comes back at 0 Hz escalates to a rebuild instead of reporting success. 41 tests. Deferred: **P4 device-verified 2026-08-23** — first-reply survival **10/10** on glasses HFP over cold sessions, and teardown clean (mic released, no lingering indicator). Route-change-mid-reply remains open: audio stopped on a glasses disconnect and it was not established whether playback carried or the loss was correctly reported. Remaining: restart-vs-rebuild ratio, and P3's playout-tail drain (needs an `async` teardown through both session managers) and P3's playout-tail drain, which needs an `async` teardown through both session managers
| [CX](CX-live-session-vision-choice.md) | Vision as a Spoken Mode | 📝 Drafted 2026-08-23 — from a device session. Starting a live session **with vision** takes a second, near-undiscoverable step: the Camera button exists only in a realtime mode, is disabled until the session is already active, and then cold-starts the glasses camera for up to **20 s** while still reading "Camera" — device-traced, the wearer pressed it repeatedly and reported streaming as broken. The obvious fix (start the camera with every live session) is rejected on four grounds, each sufficient: image tokens on every turn, the camera being the glasses' largest drain, the consent question a self-starting camera raises against `PrivacyFilterScope`, and a cold start front-loaded onto sessions that only wanted voice. Instead vision becomes a **spoken mode** — entered and left by voice, with **no wake word between questions** while it is on, and the camera warming as the mode starts so the cold start lands on a boundary the wearer chose. Suppressing the wake word is the point rather than a convenience: it makes this a *conversational* state ("we are looking at something together"), and a wearer who must re-address the assistant every question may as well take single photos. It also reads better on consent than a button — a spoken command is audible to the people around you, where a press is silent. The cost is an open mic for the mode's lifetime, so the edges are firm: explicit stop, inactivity timeout, and exits on session end, doff and thermal/power pressure, **each announced**, since a mode that ends quietly leaves the wearer believing the glasses can still see. Gated by existing policy rather than new invention: CQ's device tier (camera-less glasses never offer it) and BV's power posture (deferred and said so under `conserve`/`reserve`). **Non-goals:** auto-start without a choice; continuous narration (CV owns the unprompted case); frame-rate or dedup changes |
| [CY](CY-broadcast-resilience-and-quality.md) | Broadcast Resilience & Stream Quality | 🚧 Core shipped 2026-08-24 — **a broadcast that drops is a silent total loss**: the wearer is looking at the world, the LIVE badge stays lit, and nothing watched the RTMP connection, so a mid-stream disconnect just ended the stream while frames kept being pushed at a dead mixer. Pure cores land first — `BroadcastSessionMachine` (legal transitions as a table; a second drop report from the other status stream must not restart a reconnect already running), `BroadcastReconnectPolicy` (capped 1/2/4…60 s backoff, attempts forgiven only after a *stable* stretch so a flapping link keeps backing off, give-up budget from the first failure), `AdaptiveBitratePolicy` (down a quarter fast, up 10 % only after a sustained healthy window, and a zero throughput reading treated as a missing observation rather than starvation) and a rolling achieved-frame-rate meter. Wired thin at the edge: both connection and stream status watched, reconnect re-running the *same* connect→prime→publish path so it cannot diverge, credential rejections failing fast instead of spending the retry budget, and bitrate adaptation fed by the transport's own throughput/queue telemetry and applied mid-publish. The hardcoded 15 fps becomes `broadcastFrameRate` (default 30) everywhere it was used, timescale included, alongside new bitrate-ceiling, keyframe-interval and explicit AAC settings, an Advanced Encoding disclosure, and a live health bar (state / kbps / achieved fps / dropped frames). **P4 device+network smoke deferred** — needs a real ingest and an uplink that can be made to fail on demand |
