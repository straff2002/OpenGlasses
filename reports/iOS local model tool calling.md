# Fix the tool harness before changing models

Few open-source iOS projects run on-device tool calling at all. The ones that do are small demos and SDKs, not shipping apps. Their de facto stack is **Qwen3 or Qwen3.5 at 1.7B–4B in uniform 4-bit on mlx-swift-lm**, with **LFM2.5** as the fast alternative and **Qwen 0.6B–1.5B GGUF** on llama.cpp wrappers that compile llama.cpp's `common/chat` code. The strongest finding in the notes is about harnesses, not models. In the only controlled multi-model study, failures came mainly from three causes: parsers that did not match the model's own tool markup, tool-call turns never written back into history, and chat-template traps. Fixing these took Gemma 4 E2B from **0/6 to 6/6** and stopped Qwen3-1.7B's repeat-call loops (**10/10 → 0/10**). That bears directly on our app. Per the coordinator's reading of our source, we force every local model into Hermes `<tool_call>` JSON with tool names only, skip mlx-swift-lm's native parsers, and run single-shot. So our tool-call reliability today is probably limited by our harness more than by our model choice. The benchmark evidence for picking models is weak: every controlled accuracy figure comes from a Mac or desktop, most BFCL numbers are vendor-reported, and v3 and v4 scores cannot be compared. The recommendation therefore comes in two parts: change the harness first, then qualify a short list on device. That list is Qwen3.5-2B/4B, Gemma 4 E2B, Qwen3-1.7B and LFM3-1.7B on MLX, and Qwen3-1.7B / Qwen2.5-1.5B on GGUF, measured against Apple Foundation Models as a baseline.

## Demos and SDKs, not apps, carry on-device tool calling

On the MLX side, every verifiable project is a demo or a library. **MLX-Outil** (125 stars) demonstrates tool use with Qwen3 1.7B across iOS, macOS and visionOS, passing tools through `UserInput(chat:tools:)` ([MLX-Outil](https://github.com/rudrankriyam/MLX-Outil)). **mlx-ios-toolcall** runs a QLoRA-tuned LFM2.5-2.6B at 4-bit (`Hskyto/lfm2.5-2.6b-toolcall-mlx-q4`, trained on `xlam-function-calling-60k`). It parses with mlx-swift-lm's `.lfm2` format and routes calls to EventKit, Maps and notifications through an app-side dispatcher ([mlx-ios-toolcall](https://github.com/Hemeskyo/mlx-ios-toolcall)). **AnyLanguageModel** (990 stars) mirrors Apple's Foundation Models API over an MLX backend; its example model is `mlx-community/Qwen3.5-4B-MLX-4bit`, and MLX cannot force a tool call (`required` is "not supported") ([AnyLanguageModel](https://github.com/mattt/AnyLanguageModel)). **LocalLLMClient** marks tools experimental and uses `mlx-community/Qwen3-1.7B-4bit` ([LocalLLMClient](https://github.com/tattn/LocalLLMClient)). **SwiftAgent** supports Qwen3 only, with `Qwen3-4B-Instruct-4bit` ([SwiftAgent](https://github.com/mzbac/SwiftAgent)). The best-known open MLX chat app, **fullmoon** (~2.3k stars), has no tool calling and has had no commits since May 2025 ([fullmoon commits](https://github.com/mainframecomputer/fullmoon-ios/commits/main)). Every working example keeps execution in app code behind a name→handler dispatcher. That matches what our app already does.

mlx-swift-lm itself now treats tool calling as first-class. You pass `[ToolSpec]` and the library injects them through the chat template. Output then goes through one of **14 `ToolCallFormat` parsers** (`json`, `lfm2`, `xmlFunction`, `qwen35`, `gemma`, `gemma4`, `glm4`, `mistral`, `llama3`, `gptOSS` and others), which emit `.toolCall` and `.rejectedToolCall` events. Dispatch is fail-closed to declared tools ([ToolCallFormat.swift](https://raw.githubusercontent.com/ml-explore/mlx-swift-lm/main/Libraries/MLXLMCommon/Tool/ToolCallFormat.swift); [ChatSession.swift](https://raw.githubusercontent.com/ml-explore/mlx-swift-lm/main/Libraries/MLXLMCommon/ChatSession.swift)). The format is chosen in this order: an explicit `tool_parser_type`, then markers found in the chat template, then the model's own default. If none of these matches, it returns `nil`, and no parser runs ([ToolCallFormatInference.swift](https://raw.githubusercontent.com/ml-explore/mlx-swift-lm/main/Libraries/MLXLMCommon/Tool/ToolCallFormatInference.swift)). A community re-quantization with an edited template can therefore silently lose tool parsing. Most per-family fixes landed between 2.31.3 (April) and 3.32.3 (September 2026). 3.33.0 (17 November) added MiniCPM5 and LFM3 ([Releases](https://github.com/ml-explore/mlx-swift-lm/releases)).

Outside MLX, the stacks that give an iOS app a parser that works across model families are the ones that compile llama.cpp's `common/chat` and a Jinja engine into their binary. **llama.rn** does this ("universal tool call support by using minja"), and so does **PocketPal AI** (~9.6k stars), which is built on it and runs an `AgentRunner` tool loop for its "Talents" ([llama.rn](https://github.com/mybigday/llama.rn); [PocketPal AI](https://github.com/a-ghorbani/pocketpal-ai)). **LLM.swift** says it does the same and caps the loop at `maxToolTurns` (default 4); its example model is `unsloth/Qwen3-0.6B-GGUF` Q4_K_M ([LLM.swift](https://github.com/eastriverlee/LLM.swift)). LocalLLMClient's llama.cpp tool example is `Qwen2.5-1.5B-Instruct` Q4_K_M ([LocalLLMClient](https://github.com/tattn/LocalLLMClient)). llama.cpp's own docs still list per-family native formats (Llama 3.x, Hermes 2/3, Qwen 2.5, Mistral Nemo and others), with everything else falling to a generic JSON format ([function-calling.md](https://github.com/ggml-org/llama.cpp/blob/master/docs/function-calling.md)). The current code has replaced that list with PEG-parsed formats driven by each model's template, including a dedicated `PEG_GEMMA4`, plus lazy grammars that only engage once a call starts ([common/chat.h](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/common/chat.h)).

Other runtimes are thin. **Google LiteRT-LM** has a Swift API in "Early Preview" and runs FunctionGemma 270M in the AI Edge Gallery iOS app ([LiteRT-LM](https://github.com/google-ai-edge/LiteRT-LM)). One user reports intermittent degenerate output when its iOS API is used with native tool calling ([HF discussion](https://huggingface.co/litert-community/functiongemma-270m-ft-mobile-actions/discussions/2)). **Cactus** defaulted to `qwen3-0.6b` with tool-RAG (top-2) and confidence-based cloud handoff, but its React Native SDK was archived on 2026-07-23 ([cactus-react-native](https://github.com/cactus-compute/cactus-react-native)). ExecuTorch, MLC LLM and ONNX Runtime GenAI document no iOS tool calling ([ExecuTorch](https://docs.pytorch.org/executorch/stable/llm/run-on-ios.html)). **Apple Foundation Models** is the polished option: a `Tool` protocol with guided generation, so "tool arguments will always follow the defined arguments schema" ([Apple forum 833642](https://developer.apple.com/forums/thread/833642)). Its constraints are a **4,096-token window per session**, which tool schemas and outputs also consume, and Apple's advice of **3–5 tools** with one-phrase descriptions ([TN3193](https://developer.apple.com/tutorials/data/documentation/technotes/tn3193-managing-the-on-device-foundation-model-s-context-window.md)).

## Harness bugs, not model weakness, caused most reported failures

The best evidence in the notes is AnyLanguageModel issue #328, a controlled study across 14 models, all 4-bit MLX, on mlx-swift-lm 3.32.3. It ran on an M3 Pro Mac, not an iPhone. The MLX adapter never wrote the assistant's tool-call message into history and sent results without a call ID or name ([AnyLanguageModel #328](https://github.com/huggingface/AnyLanguageModel/issues/328)). The effects varied by family. Gemma 4 dropped the result and repeated the call. gpt-oss's template raised an error. Qwen3, Qwen3.5, Llama 3.2 and LFM2 saw a result with no call that produced it. Once the history was fixed, the numbers changed sharply: **Gemma 4 E2B 0/6 → 6/6, E2B QAT 0/6 → 5/6, E4B QAT 0/6 → 4/6; Qwen3-1.7B repeat calls 10/10 → 0/10; Qwen3-4B 8/10 → 0/10**. The same issue found two quieter bugs. The repeat-call detector compared argument dictionaries stringified in Swift's per-process hash order, so it **missed 286 of 603 identical rounds**. And an 8-round cap discarded all of the round's tool work. Apple Foundation Models, as the baseline, ran **30/30 with no errors**.

Parser coverage is the second cause. In Fae's macOS evals through mlx-swift-lm, Qwen3.5 scored 2/10 in February 2026 because it emitted `<function=…><parameter=…>` XML "rather than the JSON that mlx-swift-lm parses". Tool selection itself was correct. After the `qwen35` parser shipped, Qwen3.5-2B scored 90% and Qwen3.5-4B 100% ([Fae llm-benchmarks.md](https://github.com/saorsa-labs/fae/blob/main/docs/benchmarks/llm-benchmarks.md)). Gemma 4 had the same problem. Format inference matched `"gemma"` but not `"gemma4"`, and the parser looked for `<start_function_call>` while Gemma 4 emits `<|tool_call>`. So tool calls streamed out as plain text with `stopReason == .stop` (fixed by PRs #183 and #548) ([mlx-swift-lm #259](https://github.com/ml-explore/mlx-swift-lm/issues/259)). The most recent fix, **PR #812 (merged 2026-11-18)**, handles Qwen leaving out `</parameter>`, which let one value swallow every later argument and made the model retry until its budget ran out. It also reports calls to undeclared tools as `undeclaredTool` with the tool's name ([mlx-swift-lm PR #812](https://github.com/ml-explore/mlx-swift-lm/pull/812)). The notes conflict on tagging: the release list shows 3.33.0 on 17 November, while issue #797's title counts ~95 commits since the 3.32.3 tag. Either way, #812 landed after both tags, so **no tagged release contains it**.

The rest of the failures are template and model quirks, and they recur across runtimes. Gemma 4's template renders schemas with a recursive macro that can overflow swift-jinja's 512 KiB cooperative-thread stack on deeply nested schemas ([Layr-Labs PR #2381](https://github.com/Layr-Labs/d-inference/pull/2381)). It also crashes on a schema that omits `type` ([lmstudio #2228](https://github.com/lmstudio-ai/lmstudio-bug-tracker/issues/2228)). Qwen3.5 with thinking on often puts its tool call **inside `<think>`** and stops ([llama.cpp #20837](https://github.com/ggml-org/llama.cpp/issues/20837)). The PEG parser rejects preamble text before `<tool_call>` ([llama.cpp #20260](https://github.com/ggml-org/llama.cpp/issues/20260)). Gemma-4-E2B 4-bit returned integers and booleans as strings in one Swift build, scoring 16/20 ([eejd/swift-lm #7](https://github.com/eejd/swift-lm/issues/7)). The fine-tuned LFM2.5 iPhone demo reports that the model "sometimes [chats] instead of act[ing]" and needed a fallback pass ([mlx-ios-toolcall](https://github.com/Hemeskyo/mlx-ios-toolcall)). On grammar: llama.cpp's lazy grammars and Apple's guided generation guarantee the **syntax and argument schema of a call once one starts**. They do not decide whether to call or which tool to call ([common/chat.h](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/common/chat.h)). No source measured the speed cost of grammar-constrained decoding on an iPhone.

## Benchmarks point to Qwen3.5, Gemma 4 and LFM3, on thin evidence

No independent table covers today's small models, and the live BFCL leaderboard could not be reached in this research. Every score below comes from search-result summaries of the cited pages, so recheck each one before quoting it. Read the table by provenance and BFCL version. Some figures are vendor-reported; only a few come from independent runs. BFCL v4 adds agentic categories, so a model scores much lower on v4 than on v3. Qwen3-4B-Instruct-2507 shows the gap: **61.9 on v3 (vendor) but ~35.7 on v4 (independent)** ([HF card](https://huggingface.co/Qwen/Qwen3-4B-Instruct-2507); [benchmarklist v4](https://benchmarklist.com/benchmarks/bfcl_v4/)). Vendor and independent figures also diverge: Phi-4-mini is "70.3 BFCL" in Microsoft's table but 28.16% on independent v3 ([NVIDIA NIM card](https://docs.api.nvidia.com/nim/reference/microsoft-phi-4-mini-instruct); [benchmarklist v3](https://benchmarklist.com/benchmarks/bfcl_v3/)).

Three patterns hold up across sources. First, **uniform 4-bit is the right quantization at 2–4B, and naive 4-bit is dangerous at 1B and below**. On one function-calling subset, Qwen3-0.6B fell from 62.3% to 16.8% at Q4_K_M, while Qwen3-4B in thinking mode moved only from 94.1% to 93.5% ([arXiv 2608.22472](https://arxiv.org/pdf/2608.22472)). Fae found 4-bit better than 8-bit, bf16 or MXFP4 for Gemma 4 tool calls, and SwiftLM warns that 2-bit "heavily destabilizes JSON grammars" ([SwiftLM](https://github.com/sharpai/swiftlm)). Second, **abstention is weak everywhere**. Even xLAM-2, the best-documented small specialist, declines correctly only about 57–58% of the time on BFCL irrelevance ([APIGen-MT](https://arxiv.org/pdf/2504.03601)). Third, **parameter count is a weak predictor**: lintware's author says so explicitly, and Llama-3.2-3B scored 0.0 on restraint ([lintware](https://github.com/lintware/tool-calling-benchmark)). No source gives a tool-calling score for our Qwen2.5-0.5B, SmolLM2-360M or SmolVLM2. Given the sub-1B quantization collapse, they should not carry a tool badge without device evidence.

## iPhone memory ceilings come from per-app limits and KV cache

The iPhone figures available cover speed and memory, not accuracy. On an iPhone 17 Pro, 1B-class 4-bit models decode at **58–70 tok/s**, while Qwen3-4B and Llama-3.2-3B "couldn't fit" in one developer's app ([rickytakkar.com](https://rickytakkar.com/blog_russet_mlx_benchmark.html)). Gemma 4 E2B decodes at **49.1 tok/s on MLX, versus 61.1 on LiteRT-LM**, but MLX 4-bit **fell from 45.7 to 25.1 tok/s over 10 minutes of sustained load** ([apple-silicon-llm-bench](https://github.com/john-rocky/apple-silicon-llm-bench)). That thermal drop matters more than peak speed for an always-on assistant. On a 6 GB iPhone 15 Plus, the 4-bit LFM2.5-2.6B ran at about 1.5 GB resident and ~28 tok/s decode. The 8-bit and 16-bit builds were killed ([mlx-ios-toolcall](https://github.com/Hemeskyo/mlx-ios-toolcall)). LFM3-1.7B is about 1 GB at 4-bit [vendor] ([MarkTechPost](https://www.marktechpost.com/2026/10/27/liquid-ai-lfm3-open-weight-2b-multimodal-models/)).

The failures that should shape our design are silent ones. On an 8 GB iPhone 16 Pro with a 4,009-token prefill, **Qwen3-4B-Instruct-2507 4-bit terminated with no crash report and no jetsam event** whenever the app supplied its own KV cache. Qwen3-1.7B finished in either cache mode. The 4B model finished only with the MLX-managed cache and a 32 MB GPU cache limit. The issue is still open ([mlx-swift-examples #492](https://github.com/ml-explore/mlx-swift-examples/issues/492)). Reports on the increased-memory-limit entitlement conflict. It raised one iPhone 13 Pro from ~3.1 to ~4.2 GB available ([zenn.dev](https://zenn.dev/mtfum/articles/ios_memory_entitlements?locale=en)), but another report saw the ceiling stay at 8,192 MiB on a 12 GB iPhone 17 Pro Max regardless of entitlements ([cactus #793](https://github.com/cactus-compute/cactus/issues/793)). The notes could not confirm which of two sources holds that measurement. The two runtimes also count memory differently. MLX copies weights into the app's memory footprint, while llama.cpp memory-maps them ([Vocello doc](https://github.com/PowerBeef/Vocello/blob/main/docs/reference/ios-increased-memory-entitlement-request.md)). One app found that Gemma 4 does not fit at all on a phone where iOS holds about 3 GB it cannot hand back ([private-mind PR #457](https://github.com/software-mansion-labs/private-mind/pull/457)). Finally, iOS rejects Metal command buffers submitted in the background, whatever audio or background modes the app holds. llama.cpp aborts the process if the app is minimized during decode ([llama.cpp #16998](https://github.com/ggml-org/llama.cpp/issues/16998)). For a glasses app that is often backgrounded, this is a correctness requirement, not tuning.

## Our harness, not our catalog, is the first thing to change

What follows comes from the app's code, not from the notes. The coordinator read the source on 2026-11-20, and I checked two points myself. On the MLX path, `LLMService.localToolInstructions` lists tool names only, with a hand-written schema for `calendar` alone. It tells every model to emit Hermes `<tool_call>` JSON. `LocalLLMService` discards mlx-swift-lm's `.toolCall` events, and `LocalOutputPolicy` parses only the Hermes frame and bare JSON. The turn is single-shot with one optional regeneration. The catalog marks MLX Gemma 4 E2B/E4B and Qwen2.5 3B/0.5B `.toolFriendly` from a hard-coded list (`toolCapableModelIDs` in `OpenGlasses/Sources/Services/LocalInference/LocalModelCatalog.swift`). mlx-swift-lm is pinned to revision 14414441, which almost certainly predates PR #812. I checked the GGUF path: the vendored `llama.xcframework` (llama.cpp v0.3.0, commit c1d0e7a) ships only core headers. Our wrapper renders prompts through `llama_chat_apply_template`, which `llama.h` says "does not use a jinja parser" and supports only a predefined list of templates. So **the GGUF path has neither `common/chat` tool parsing nor template-driven tool injection**. It does have `llama_sampler_init_grammar` for GBNF. `com.apple.developer.kernel.increased-memory-limit` is already in `OpenGlasses/OpenGlasses.entitlements`.

Set against the notes, our design reproduces each harness failure the controlled study isolated. For Qwen2.5, Hermes JSON is the model's native format, so the current prompt happens to be on-distribution. For Gemma 4, the native format is `<|tool_call>call:name{…}<tool_call|>`, which mlx-swift-lm parses after #183 and #548. Asking Gemma 4 for Hermes JSON without schemas throws away exactly the template and parser work that took it to 6/6 and 100% in independent runs. Qwen3.5, LFM2.5 and LFM3 would be off-distribution in the same way. Single-shot generation also skips the tool-call round-trip that fixed most #328 failures. And because we pass no argument schemas, none of the typed fixes can apply: schema-typed argument conversion (#167, #388), undeclared-tool rejection, and later grammar constraints. One counterpoint deserves weight. Field Assist's retrieval tools (`manual_lookup`, `document_knowledge`, `show_source`) are tools whose information is always needed. Apple's guidance is to run those deterministically before the model and inline the results rather than ask a small model to choose them ([TN3193](https://developer.apple.com/tutorials/data/documentation/technotes/tn3193-managing-the-on-device-foundation-model-s-context-window.md)). Combined with ~57% abstention at best, that argues for enforcing the "hold when the answer is not in the passages" rule in code, never trusting the model to decline.

### Models to put through device qualification, in order

| # | Model and artifact | Runtime | Why it is on the list | What would disqualify it |
|---|---|---|---|---|
| 1 | Gemma 4 E2B-it, uniform 4-bit (not QAT, not MXFP4) | MLX, native `gemma4` format | Already shipped; strongest independent post-fix results (6/6, 100%); vision and audio | Thermal drop below usable speed; template crashes on our schemas |
| 2 | Qwen3.5-2B, then Qwen3.5-4B, 4-bit, thinking off on tool turns | MLX, `qwen35` format + #812 | 90% / 100% in Fae; the current ecosystem default; vision | 4B: the silent termination pattern from #492 on 8 GB phones |
| 3 | Qwen3-1.7B 4-bit | MLX and GGUF Q4_K_M | Most-used demo default; top of lintware's run; fits in either cache mode on an iPhone 16 Pro | No vision; v3/v4 scores unverified |
| 4 | LFM3-1.7B 4-bit (Liquid's own build) | MLX (support merged Nov 2026) | Best vendor BFCL v4 per parameter; ~1 GB | Licence terms; needs an mlx-swift-lm revision with LFM3 support and a working parser for its new XML format |
| 5 | Qwen2.5-1.5B Q4_K_M (current GGUF) as the GGUF control | llama.cpp, Hermes | Native Hermes format matches our parser; LocalLLMClient's tool example | Below Qwen3-1.7B on the same tasks |
| — | Apple Foundation Models | System (iOS 26+, Apple Intelligence devices) | 30/30 in #328; schema-guaranteed arguments; the yardstick | 4K window; no version pinning; not on our iOS 17.2 floor |

Remove the tool badge from Qwen2.5-0.5B (MLX) and from Qwen2.5-0.5B and SmolLM2-360M (GGUF) until device evidence exists. If a sub-1B model must route tools, qualify it at Q8_0 or 8-bit, given the Q4 collapse. Keep Qwen2.5-3B only if it beats Qwen3.5-2B in the same run, since no source gives it a tool score. Hold xLAM-2 and Hammer2.1 until their licences are confirmed.

## Conclusion

The question "which model should we qualify" is downstream of a design decision our app made when on-device tool APIs were immature. That decision was one universal markup, no schemas and no round-trip. In late 2026 it is the main thing standing between our shipped models and the reliability independent runs report for them. Gemma 4 E2B, which we already ship, looks broken under a Hermes-without-schemas harness and near-perfect under its native format with history round-tripped. Our own device results would be unreadable until the harness changes, so qualifying new models first would measure our harness, not the models.

The deeper lesson for Field Assist is that model accuracy and abstention are different problems. Grammar, native parsers and round-tripping can make calls well-formed and stop loops. Nothing in the evidence makes a 2–4B model reliably decline, and the best small specialist declines correctly only about 57% of the time. A model's "I don't know" should therefore be enforced in code from retrieval results, and Apple Foundation Models' 30/30 run is the bar any MLX candidate has to clear on our own tools to justify its download size. The open unknowns are sharp and testable: no source has an iPhone-measured tool-call success rate for any model, LFM3's numbers are only Liquid's own, and BFCL v3 and v4 figures cannot be compared. A one-week on-device run of the five-model list above, after the P0 changes, would replace most of this report's inference with our own measurements.
